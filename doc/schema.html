Novel-to-Screenplay 剧本 YAML Schema 规范文档

本规范定义了由小说文本（三章以上）自动化改编为影视剧本时的结构化数据交换格式（YAML Schema）。通过该 Schema，AI 提炼的文学内容能够无缝转换为可编辑、可直接用于生产环境的结构化剧本数据。

一、为什么选择 YAML 格式？

在传统的软件工程中，结构化数据通常首选 JSON 或 XML。然而在本创作工具中，我们选择 YAML (YAML Ain't Markup Language) 作为剧本输出格式，核心设计原因如下：

  • 极佳的可读性（Human-Readable）： 剧本的本质是文学与影视的结合，创作者（编剧、导演）需要高频阅读剧本。YAML 没有 JSON 复杂的层层大括号 {} 和方括号 []，也没有 XML 冗长的标签，极其契合剧本所要求的干净、无干扰的阅读体验。
  • AI 生成稳定性（LLM Friendly）： 大语言模型在输出文本时，符号越少，语法出错（如漏掉逗号、括号不匹配）的概率就越低。YAML 依靠严格的换行和缩进表达层级，能有效缩减 Token 消耗，并极大提升 AI 一次性生成长剧本的成功率。
  • 易于人工二次打磨： 生成的剧本是初稿，编剧后续可在任意文本编辑器中直接修改、增删台词，格式不易崩塌。

二、YAML Schema 定义

以下为标准的剧本数据骨架及节点约束：

screenplay:
  meta:
    title: string          # 作品/剧本名称
    genre: string          # 题材类型（如：悬疑、爱情、科幻）
    author: string         # 原著作者
    adapter: string        # 改编者（固定为 "Novel-to-Screenplay AI"）
    version: string        # 剧本版本号（初稿默认为 "1.0"）
    logline: string        # 故事一句话简介（故事线，不超过50字）

  characters:              # 角色档案列表（全局去重）
    - name: string         # 角色姓名
      role: string         # 角色定位（protagonist/antagonist/supporting/minor）
      description: string  # 角色外貌、性格及原著背景简述

  acts:                    # 幕（Act）级别切分
    - act_number: integer  # 幕序（标准三幕式：1, 2, 3）
      title: string        # 本幕核心冲突或主题
      scenes:              # 场景（Scene）列表
        - scene_id: string           # 唯一场景编号（采用 A1S1 即第一幕第一场格式）
          chapter_source: string     # 映射的原著小说章节（如 "第一章"）
          location: string           # 场景发生地点（日景/夜景、室内/室外）
          time_of_day: string        # 发生时间段（DAY/NIGHT/DAWN/DUSK/CONTINUOUS）
          atmosphere: string         # 舞台氛围说明（如：阴冷、死寂、剑拔弩张）
          beats:                     # 场景内的最小戏剧行为单元（信息流/节拍）
            - type: string           # 单元类型（action/dialogue/transition）
              character: string      # 说话者姓名（仅当 type 为 dialogue 时必填）
              content: string        # 舞台动作叙述 或 台词具体内容
              direction: string      # [可选] 角色说台词时的语气、动作指导

三、Schema 关键节点设计原因分析

1. 全局 characters 角色档案的必要性

设计原因： 在传统剧本中，人物是在每场的对白里直接登场的。但本 Schema 在顶层抽离出了一个全局的角色列表。这样做是为了方便在 AI 处理完长小说后，自动帮作者梳理并归纳出一份人物设定表（Cast List）。它为每个角色标注了 role（如主角、反派、配角），使得制片方和选角导演能一眼评估出整部戏的演员体量，大大降低了通读小说的门槛。

2. acts (幕) 与 scenes (场景) 的双层嵌套

设计原因： 小说通常按“章节”划分，而电影、网剧剧本则是按“场景”划分。单章小说往往包含大量的空间移动。本工具没有简单地把“一章”变成“一场”，而是引入了经典的好莱坞三幕式（Three-act structure）宏观结构，将章节智能打碎并重新归纳进 acts 节点。场景编号采用 A1S1 (Act 1, Scene 1) 格式，契合工业级影视工业标准，便于跨部门（导演组、摄影组）拉片和排戏。

3. beats (戏剧节拍) 的多类型（Type）抽象

设计原因： 剧本内部的文本信息极度异构，包含环境描写、动作指导、潜台词和声音效果。我们将场景内部拆解为 beats（节拍）数组，并通过 type 字段严格限制为三种：

Type 类型 对应剧本元素 设计初衷
action 舞台说明/动作叙事 承接小说的环境描写与心理描写的具象化动作表达。
dialogue 角色台词对白 提取原著对白，绑定说话者 character，支持 direction（语气括号）。
transition 场景转场特效 提供诸如【淡出】、【闪回】等电影视听语言标记。
文档结论： 本 Schema 并非简单的“小说格式化”，而是将非结构化的长篇文学叙事，重构成了一套符合数字影视工业标准的、可被计算机程序解析并高亮渲染的数据模型。
